# Orlumi AI Collaboration Rules

## Mandatory Reading

Before editing this repository, an AI assistant must read in order:

1. `docs/ORLUMI_BIBLE.md`
2. `docs/WEBSITE_GUIDE.md`
3. the specialist guide relevant to the requested change
4. the current implementation

The current code does not override documented brand decisions.

## Core Obligations

Always preserve these truths:

- Orlumi is the parent brand for multiple worlds.
- The homepage must not become a single-game landing page.
- Use `Our Worlds` in brand-facing navigation and headings where appropriate.
- The ancient tree remains unnamed and unexplained.
- Little Explorer and Petal Nook are distinct titles; release order is not fixed unless explicitly updated.
- Orlumi should feel calm, warm, curious and quietly magical.

## Never Do Without Explicit Approval

- rename Orlumi or an official title
- name the ancient tree
- publish a release date
- invent game mechanics, characters or platform availability
- introduce shared canon between games
- change the primary brand line
- replace the palette or typography direction
- add tracking, advertising or data collection
- add a newsletter or contact form that stores personal information
- redesign the site into a SaaS, corporate or high-stimulation children’s style

## Design Guardrails

Do not:

- use neon colours
- add flashing or rapid animation
- overuse glow, sparkles or particles
- use excessive saturation, especially sharp yellow
- hide essential content behind animation
- remove focus indicators
- use decorative art that harms readability
- rely on emoji as finished brand artwork

## Lore Guardrails

Do not treat brainstorms as canon.

When writing lore:

- distinguish confirmed facts from possibilities
- prefer fragments and motifs over exposition
- do not explain the tree’s origin or full nature
- do not directly combine Peggy, Fenwick and Persephone into public names
- update `LORE.md` only after explicit owner approval

## Copy Guardrails

- Use factual status wording.
- Do not claim `coming soon` unless that status is approved.
- Do not create fake Google Play buttons.
- Do not use manipulative urgency.
- Keep copy clear before making it poetic.

## Technical Guardrails

- Keep the site responsive and progressively enhanced.
- Content must remain available if JavaScript fails.
- Respect `prefers-reduced-motion`.
- Avoid unnecessary frameworks and dependencies.
- Optimise images and prevent layout shift.
- Keep secrets and personal credentials out of the repository.
- Do not introduce analytics or third-party scripts silently.

## Change Procedure

For each substantial change:

1. Identify the owner’s request.
2. Check it against the Bible and specialist guide.
3. State any conflict before implementation.
4. Make the smallest coherent change.
5. Update documentation when the decision changes.
6. Verify responsive, accessibility and content accuracy.
7. Report exactly what changed and what remains provisional.

## Uncertainty Rule

When information is missing:

- do not invent it
- use a clearly marked placeholder only when necessary
- preserve structural flexibility
- record the unresolved decision in `ROADMAP.md` if it blocks future work

## Definition of Success

A successful AI-assisted change makes Orlumi clearer, more coherent or more usable without making it louder, more generic or more fully explained.
